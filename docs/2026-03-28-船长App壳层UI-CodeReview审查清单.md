# 2026-03-28 船长App壳层UI Code Review审查清单

## 1. 文档目标

本文档用于审查船长 App 主壳层 UI 相关改动，确保后续需求持续遵守以下目标：

- 年轻化但不过甜
- 水果感但不幼态
- 简洁大方但不单薄
- 风格统一且不回退到旧工具页气质

本清单适用于以下范围：

- 首页
- 底部 Tab
- 顶部欢迎区 / 标题栏
- “我的”页
- 颜色、字号、圆角、间距、按钮、卡片等壳层资源

## 2. 使用方式

每次涉及壳层 UI 的改动，Code Review 必须逐项检查。

判定规则：

- `通过`：符合规范，无明显回退
- `需修改`：有偏差，但改动成本低，应在当前 PR 修正
- `打回`：破坏既定标准，或新增不可控特例，不允许合入

## 3. 必查项

### 3.1 颜色

- 是否新增了硬编码颜色值
- 是否绕开既有颜色 token 直接写品牌粉、品牌橙、品牌绿
- 是否把品牌主色错误用于长段正文
- 是否出现一页内 3 个以上高饱和主色块
- 是否把浅底托和浅文字叠在一起导致可读性变差

打回条件：

- 直接在布局或代码里新增品牌色 hex
- 重要文字对比度明显不足
- 页面整体颜色明显偏甜或偏杂

### 3.2 字号与文案层级

- 是否仍全部使用 `sp` 定义字体大小
- 是否出现多个接近但不同的标题字号
- 是否为了塞内容缩小了主标题、主按钮或列表主文案字号
- 品牌轻文案是否误用在隐私、权限、删除、错误、保存结果等严肃场景

打回条件：

- 新增 `dp/dip` 文本尺寸
- 高风险场景使用品牌口号替代功能说明

### 3.3 间距与圆角

- 是否复用了既有圆角 token 和间距 token
- 是否出现仅在单页使用的特殊圆角
- 是否因为业务堆叠把模块间距压得过紧
- 是否把页面重新做回“密、挤、碎”的旧工具页感

打回条件：

- 新增无语义圆角
- 大量使用 magic number 压布局

### 3.4 组件尺寸底线

- 底部 Tab 是否仍保持 `64dp` - `68dp`
- Tab 图标是否仍为 `24dp`
- 主按钮高度是否不低于 `44dp`
- 列表项高度是否不低于 `56dp`
- 点击区是否被压缩到影响可用性

打回条件：

- 为了更“精致”缩小按钮、Tab、列表项点击区域
- 组件尺寸回退到旧版粗糙或不稳定状态

### 3.5 首页结构

- 首页是否仍遵守“欢迎区 + 功能区”的主骨架
- 若存在推荐区，是否有真实依据而不是伪内容
- 是否新增了装饰性卡片、伪入口、空模块
- 功能卡片是否仍然是“真入口”

打回条件：

- 仅为了丰富页面新增无业务意义模块
- 推荐区无真实推荐依据
- 首页重新回退成九宫格工具墙或拼装页

### 3.6 “我的”页结构

- 是否仍是“品牌卡 + 简介卡 + 功能列表卡”的分组结构
- 是否把“我的”页重新做成大段说明堆叠
- 列表项是否仍保持统一风格
- 是否新增情绪化但无功能价值的内容块

打回条件：

- “我的”页退化为说明页
- 列表项风格明显与主壳层脱节

### 3.7 图标与视觉风格

- 首页卡片图标、Tab 图标是否风格统一
- 是否出现一部分图标偏插画，一部分偏系统图标的混搭
- 是否新增过多阴影、描边、发光效果

打回条件：

- 图标语言明显不统一
- 页面出现明显装饰过度

## 4. 例外规则

允许存在例外，但必须满足以下条件：

1. 由真实业务强约束驱动
2. 在 PR 描述中明确说明原因
3. 写明影响范围
4. 说明是否需要后续回收

不允许的例外理由：

- “这样更好看”
- “先这么写，后面再说”
- “只这一页特殊”

## 5. 审查结论模板

建议 Review 结论按以下格式输出：

1. 结论
   - `通过 / 需修改 / 打回`

2. 主要问题
   - 列出不符合项

3. 必改项
   - 当前 PR 内必须修掉的项

4. 可后续优化项
   - 不阻塞本次合入，但需要记录的问题

## 6. 总结

这份清单的意义，不是让每个页面都长得一模一样，而是防止后续需求一边做一边把标准打散。只要颜色、字号、结构、文案、组件尺寸、图标风格这 6 条线不失控，船长 App 的壳层 UI 就不容易变形劣化。

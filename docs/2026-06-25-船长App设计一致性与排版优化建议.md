# 船长App 全App设计审计：从「水果色 token 表」到「颜色即状态」

> **落地纪要（2026-06-25，已实施并通过 `:captain:assembleDebug`）**
> 本文 P0/P1/P2 已全部落地到代码。关键决策与原建议的偏离记录如下：
> - **P0-1 取「以规范为准改代码」**（与原文推荐相反）：`colors.xml` 已改为 2026-03-28 规范值，品牌主色回到 `#FF8A8F`。代价：主按钮白字对比 ~2.3:1，未达规范 §3.6 的 4.5:1（已知，留作后续把按钮文字改深色或加深品牌色补救）。
> - **P1-5 品牌状态色阶锚点改为 `#FF8A8F`（700）**，非原文的 `#F56B7D`；`captain_brand_primary` 现为 `→ captain_brand_700` 的别名。
> - **P0-4 修正**：Timer 昼夜是「按时段/天气 `isDay()` 运行时切换」，不是系统深色模式。已把 hex 抽进 `values/timer_colors.xml`（94 个 day/night token），但**保留 `day?:` 分支**，未移入 `values-night`。
> - **P1-8 暗色为「就绪未启用」**：`values-night/colors.xml` 已建对称层，但 `AppTheme` 仍为 Light、未切 DayNight——因大量图标/头像矢量尚未 token 化，贸然启用会半黑。启用前需：① 切 `Theme.AppCompat.DayNight` ② 各表面/图标全部 token 化 ③ 真机 QA。
> - 其余 P0-2/P0-3/P1-6/P1-7/P2-9~12 已按本文落地。

## 审计结论

船长 App 已有一套命名规整的 `captain_*` token，但它只是「一张色板」，不是「一套系统」。最致命的是两点。

其一，规范与代码已严重漂移。既有规范文档（2026-03-28）里的核心色值、字重要求、`size_tab_height` 几乎全部与 `colors.xml`/`dimens.xml`/`styles.xml` 的真实值对不上，任何按文档取值的人都会做错。

其二，整套 token 只编码了「色值」，没有编码「状态」。没有任何一个 token 回答「按钮按下该深多少」「边框态用哪一档」「暗色态从哪来」，于是状态层全部失控：Timer 模块在 Canvas 里手写了 91 处 hex 字面量、39 处 `day?A:B` 昼夜三元式，XHS 模块另起 11 个独立命名空间，legacy `colorPrimary` 死 token 仍被布局直接引用，暗色这一等公民被困在自绘代码里无法被规范约束。

本文按 P0（一致性硬伤）/P1（对标 Geist 状态色阶）/P2（排版更美）给出可逐项落地、可勾选验收的整改路径。

### P0-2 XHS 命名空间脱离 captain 体系

**【现象】** `colors.xml` 第 67–77 行有 11 个 `xhs*` 颜色（`xhsPrimary #E64A5B`、`xhsPageBackground #F4F6FB`、`xhsTextPrimary #182230`、`xhsSuccess #1C8E57`、`xhsError #D64545`、`xhsWarning #B26A00` 等），完全脱离 `captain_*` 命名与色系：背景是冷灰蓝 `#F4F6FB`（captain 体系是暖粉白 `#FFF9F7`），主色是 `#E64A5B`（captain 是 `#F56B7D`）。命名用 camelCase，与全项目 snake_case 的 `captain_*` 不一致。

**【为什么伤一致/美】** 同一个 App 里出现了两套互不知道对方存在的色彩语言：暖粉果感 vs 冷灰蓝。用户从首页进 XHS 模块会感到「换了个 App」。`xhsSuccess/xhsError/xhsWarning` 与 captain 的 `captain_feedback_*` 各自定义了一遍，正是规范 2.2「复用优先」的反例。

**【为什么这里要保留差异化】** XHS 是嵌入第三方内容场景，适度向小红书原生视觉靠拢有合理性。所以**不强行抹平主色**，但要做两件事：语义对齐 + 命名归一。

**【建议】**
1. 命名归一：全部 11 个加 `captain_xhs_` 前缀、转 snake_case，纳入命名空间（如 `xhsPrimary` → `captain_xhs_brand_primary`，改 `colors.xml`）。
2. 语义复用：`xhsSuccess/xhsError/xhsWarning/xhsDivider/xhsTextPrimary/xhsTextSecondary` 这 6 个**通用语义**直接指向 captain 主 token（如 `xhsError` → alias `@color/captain_feedback_error`），不再独立定义色值；仅保留 `captain_xhs_brand_primary`、`captain_xhs_brand_primary_dark`、`captain_xhs_page_background`、`captain_xhs_selection_mask`、`captain_xhs_surface` 这 5 个真正差异化的。
3. 圆角收敛：XHS 内若存在私有圆角，改用 P2-10 收敛后的 `captain_radius_card`（16）/`captain_radius_card_large`（20）。
4. 文字 hardcoded 全部替换为 `@color/captain_xhs_text_*`。

**【验收】**
- [ ] `colors.xml` 中不再有 camelCase 颜色名，全部 `captain_` 前缀
- [ ] XHS 的 success/error/warning/divider/text 已指向 captain 主语义 token
- [ ] XHS 布局/绘制内无私有圆角值
- [ ] XHS 模块内 grep 不到 `#` 开头的文字颜色 hardcoded

### P0-3 legacy 死 token：Material 靛蓝与 captain 果粉并存，且仍被布局直接引用

**【现象】** `colors.xml` 第 60–62 行仍保留 `colorPrimary #3F51B5`（Material 靛蓝）、`colorPrimaryDark #303F9F`、`colorAccent #FF4081`（Material 粉），注释「保留用于兼容性，逐步迁移」。`styles.xml` 第 7–9 行的 `AppTheme` 已把 `colorPrimary` 这一 attr 指向 `@color/captain_brand_primary`。

**关键纠偏：这三个色值并非「已无引用」。** grep 实测发现 `res/layout/normal_item_detail_info_view.xml:15` 直接写了 `android:background="@color/colorPrimary"`，会渲染出 Material 靛蓝 `#3F51B5`，与全 App 暖粉色彻底撞色。`res/layout/app_bar_base.xml:19` 用的是 `?attr/colorPrimary`（主题 attr，会解析为品牌色，不受影响），与 `@color/colorPrimary` 是两回事。

**【为什么伤一致/美】** 死 token 是已经引爆的炸弹，不是潜在风险：`normal_item_detail_info_view` 这块背景此刻就是靛蓝。注释说「逐步迁移」但只迁了主题 attr，色值本体和它的直接引用都还在，迁移做了一半。

**【建议】** 不能盲删，须先迁移引用再删 token：
1. 把 `normal_item_detail_info_view.xml:15` 的 `@color/colorPrimary` 改为 `@color/captain_brand_primary`（或按该视图语义选用合适的 `captain_*` 色）。
2. 复核 `?attr/colorPrimary` 类用法保持不动（它走主题，已指向品牌色）。
3. 再次 grep 确认无残留：`grep -rn "@color/colorPrimary\|@color/colorAccent\|@color/colorPrimaryDark" captain/src`，结果为空后，删除 `colors.xml` 第 60–62 行三个 token。
4. `styles.xml` 第 7–9 行 `AppTheme` 的 `colorPrimary/colorPrimaryDark/colorAccent` 是 AppCompat 框架要求的 attr 名（非颜色名），保留不动、继续指向 `captain_brand_primary/accent`。

**【验收】**
- [ ] `normal_item_detail_info_view.xml` 已不再引用 `@color/colorPrimary`
- [ ] 全工程对 `@color/colorPrimary`/`@color/colorAccent`/`@color/colorPrimaryDark` 的直接引用 grep 为空
- [ ] `colors.xml` 第 60–62 行三个死 token 已删除
- [ ] App 编译通过，原靛蓝背景块变为果粉品牌色

### P0-4 Timer 模块 91 处 hex / 39 处昼夜三元式游离于 token 外

**【现象】** `timer/` 目录下 `TimerBackgroundPainter.java`、`TimerWaterPainter.java`、`TimerControlPainter.java`、`TimerChannelView.java`、`TimerTopInfoPainter.java` 五个绘制类共出现 **91 处 hex 字面量**（按文件：58 / 13 / 10 / 6 / 4）与 **39 处 `day?...:...` 昼夜三元式**（按文件：19 / 10 / 5 / 3 / 2）。二者是两个独立量级——一处 `day?A:B` 通常含 2 个 hex，39 处三元式并不等于「91 中的 39」。典型：
- `TimerBackgroundPainter` 第 15–18 行四组季节渐变数组 `DAY_TOP={0xFFEAF8F1,…}` / `DAY_BOTTOM` / `NIGHT_TOP={0xFF102433,…}` / `NIGHT_BOTTOM`，**4 个数组各 4 个端点共 16 个 hex**；
- `TimerWaterPainter` 第 77 行 `paint.setColor(day?0x334CA7D8:0x338CD8FF)`（水滴色）、第 33–34 行 `day?0xFFE9E0D8:0xFF58606B`（石面渐变）；
- 文字/阴影 `day?0x35FFFFFF:0x18FFFFFF`、`Color.argb(alpha,74,167,216)` 等 RGB 散值。

全部 hex 直接写死在 Java 里，**没有一个走 `@color` token**，昼夜两套色彩既不能被规范约束，也无法在别处复用。

**【为什么伤一致/美】** 这是「被困在 Canvas 里的暗色状态层」：Timer 的夜间态其实就是全 App 应该拥有的 dark theme，但它被锁死在自绘代码里，既享受不到 token 治理，也无法反哺主壳。改一次品牌色，Timer 的季节渐变端点不会跟着动，日积月累必然与主壳脱色。39 处 `day?A:B` 还把「昼夜切换」这个本该由系统 `values-night` 资源限定符统一处理的能力，降维成散落各处的手写分支，极易漏改、错配。

**【建议】** 分两步，第二步并入 P1-8：
1. **抽 token**：把这 91 个 hex 按语义命名进资源——日间组进 `values/colors.xml`，夜间组进 `values-night/colors.xml`，如 `captain_timer_water_drop`（日 `#334CA7D8`/夜 `#338CD8FF`）、`captain_timer_season_top_spring`（日 `#EAF8F1`/夜 `#102433`）……季节渐变数组改为从 `R.color` 数组资源（`<array>`/`obtainTypedArray`）读取。
2. **删昼夜分支**：抽 token 后，39 处 `day?...:...` 退化为「读同一个 `@color`，由系统按 `values`/`values-night` 自动选」，Java 里不再有用于选色的 `day?` 三元式（`day` 仅保留用于几何/动画差异，不用于选色）。

**【验收】**
- [ ] `grep -rEn "day\s*\?\s*0x" timer/*.java` 为 0（昼夜不再在 Java 里选色）
- [ ] `timer/` 五个绘制类内 hex 字面量数显著下降（目标：仅留几何/alpha 计算用的非色值）
- [ ] 新建 `values-night/colors.xml` 承载全部 Timer 夜间色
- [ ] 系统切深色后 Timer 夜间态由资源限定符驱动，视觉无回归

### P1-6 elevation 三档替代唯一的 tab_shell

**【现象】** `dimens.xml` 第 58 行仅有 `captain_elevation_tab_shell=10dp` 一个 elevation token，卡片、弹层、模态无分档，实际靠各 drawable 自带阴影或散值。

**【为什么伤一致/美】** 没有 elevation 分层，卡片和弹窗可能用同一阴影，Z 轴层级混乱；深色态下阴影几乎不可见，需要靠「表面提亮」表达层级，而当前完全没有这套映射。

**【建议】** 按 Geist 三档，在 `dimens.xml` 落地 `captain_elevation_raised=2dp`（卡片）、`captain_elevation_popover=8dp`（下拉/气泡）、`captain_elevation_modal=16dp`（对话框/底部弹窗），`tab_shell` 归入 `raised` 或保留为特例。深色态在 `values-night` 中改用「表面叠色」表达层级（`captain_surface_raised`/`_popover`/`_modal` 逐档提亮），而非纯靠投影。

**【验收】**
- [ ] `dimens.xml` 含 raised/popover/modal 三档 elevation
- [ ] 卡片用 raised、弹层用 popover、对话框用 modal，无混用
- [ ] `values-night` 提供对应表面叠色 token，深色层级可辨

### P1-7 motion token

**【现象】** 全工程无 duration/easing token，动效时长散落在各处属性动画与 Timer 自绘的手写相位里，无统一缓动，未尊重系统「减弱动效」。

**【建议】** 新建 `values/integers.xml` 落地 `captain_motion_instant=0`、`captain_motion_state=150`、`captain_motion_popover=200`、`captain_motion_overlay=300`（ms），缓动统一用 `FastOutSlowInInterpolator`（标准缓动）。在动画入口读取 `Settings.Global.ANIMATOR_DURATION_SCALE`，为 0 时跳过过场动画（reduced-motion）。Timer 的环境动画（雨雪相位）属装饰性，在 reduced-motion 下降级为静态帧。

**【验收】**
- [ ] 状态切换 150ms、弹层 200ms、遮罩 300ms，取自 token
- [ ] 全 App 缓动统一为标准缓动曲线
- [ ] 系统关闭动画时，过场/装饰动效降级，核心功能不受影响

### P1-8 双主题对称：把 Timer 夜间提炼为一等 dark token 层

**【现象】** 当前唯一的「暗色」存在形式就是 P0-4 里 Timer 的 39 处 `day?...:NIGHT…` 分支，主壳层（首页/我的）**完全没有暗色态**。暗色不是一等公民，而是 Timer 模块的私货。

**【为什么伤一致/美】** Geist 双主题原则：同一套语义 + 状态，深浅只换映射不换结构。现在结构是断裂的——Timer 自己有一套夜，主壳没有夜，二者无法对称。用户系统开深色，主壳刺眼、Timer 漆黑，体验割裂。

**【建议】** 建立 `values-night/colors.xml`，让 P1-5 的全部语义 token（brand/gray/feedback/surface）在深色下**只换映射、不换名字**：如 `captain_surface_page` 在 night 下映射为深色底、`captain_gray_1000`（文字）与 `captain_gray_100`（背景）在 night 下对调明度方向。P0-4 抽出的 Timer 夜间色并入此层。主壳 `AppTheme` 增加 `values-night` 变体，使首页/我的页同步获得暗色。验证「同一 XML 布局，不改一行，切换 night 资源即得对称深色态」。

**【验收】**
- [ ] 存在 `values-night/colors.xml`，覆盖全部语义 token
- [ ] 主壳首页/我的页在系统深色下有正确暗色态，非黑屏/非刺眼
- [ ] Timer 夜间色并入 night 层，与主壳共用同一套语义名
- [ ] 浅/深两套仅映射不同，token 名与结构完全一致

## P2 排版更美（跟随 P1）

### P2-9 字阶字重：`sans-serif-medium`（≈500）冒充 600，缺字距/行高

**【现象】** `styles.xml` 第 57–81 行，`CaptainText.Hero/PageTitle/CardTitle/Overline` 全部用 `fontFamily=sans-serif-medium`（≈500 字重），而规范第 4.2 节要求标题 `weight_semibold=600`——**代码用 500 冒充了 600**。`letterSpacing` 仅在 `Overline`（0.08）出现，其余标题/正文无字距、无显式 `lineSpacing`。`Overline` 另叠了 `textStyle=bold`，与 `sans-serif-medium` 叠加后字重表现不可控。

**【为什么伤一致/美】** Geist 排版靠「字号+字重+行高+字距协同」建立层级，而非单一加粗。当前 Hero（22sp/medium）与 PageTitle（20sp/medium）字号近、字重同，层级仅靠 2sp 区分，标题不够「立」；大标题无负字距显松散，正文无行高在中文长段落里发挤。

**【建议】** 按 Geist 拆 heading/label/copy/button 四类，在 `styles.xml` 补齐：
- **heading**（Hero/PageTitle/CardTitle）：字重升到真 600——用 `android:textFontWeight="600"`（minSdk≥28）或随包提供 semibold 字体文件，不再靠 `sans-serif-medium`+`bold` 凑；Hero 加 `letterSpacing=-0.01`（收紧），`lineSpacingMultiplier=1.2`。
- **label**（Overline/Tab/Badge）：500，`letterSpacing=0.04~0.08`，小字号微扩字距；去掉 `Overline` 的 `bold` 叠加。
- **copy**（Body/Caption）：400，`lineSpacingMultiplier=1.5`（中文正文行高），字距 0。
- **button**：500–600，字距 0，行高 1。

**【验收】**
- [ ] 标题样式实际渲染字重为 600（非 medium+bold 凑）
- [ ] Hero/PageTitle 在字号近似时，靠字重+字距拉开可辨层级
- [ ] 正文 `CaptainText.Body` 设置 ≥1.4 的行高
- [ ] 四类样式各自成阶，`styles.xml` 注释标明 heading/label/copy/button 归属

### P2-10 圆角碎片化 12/14/16/18/20/24 → 收敛四档

**【现象】** `dimens.xml` 第 15–21 行圆角有 7 个值、6 个不同档：`card_large=20`、`card=16`、`button=14`、`badge=12`、`avatar=24`、`icon_tile=18`、`tab_shell=24`。其中 `button=14`、`icon_tile=18` 与 4 的倍数体系（其余多为 4 的倍数）对不齐，`14` 和 `18` 是孤值。

**【为什么伤一致/美】** Geist 圆角克制原则：控件/卡片/容器/pill 四档不混用。6 档圆角中 14/18 这种「不上不下」的值，让按钮和图标块的弧度与卡片体系对不齐，近看就是「每个角都差一点」的不精致。

**【建议】** 收敛为四档（控件/卡片/容器/pill），落地到 `dimens.xml`：
- `captain_radius_control=12dp`（按钮/badge/输入框）——`button` 从 14 收到 12，`badge` 保持 12；
- `captain_radius_card=16dp`（常规卡片）——不变；
- `captain_radius_container=20dp`（大容器/icon_tile/tab_shell）——`icon_tile` 从 18 升到 20，`card_large` 保持 20，`tab_shell` 从 24 收到 20 统一；
- `captain_radius_pill=9999dp`（头像/胶囊）——`avatar` 用 pill 或保留 24 圆形。
消灭 14、18 两个孤值。

**【验收】**
- [ ] `dimens.xml` 圆角仅剩 control/card/container/pill 四档
- [ ] 全工程 grep 不到 14dp、18dp 圆角
- [ ] 按钮与 icon_tile 弧度与卡片体系成倍数关系

---

### P2-11 间距：block 与 hero_inner/page_bottom 都用 24，缺区块级呼吸

**【现象】** `dimens.xml` 中 `captain_space_hero_inner=24`、`captain_space_block=24`、`captain_space_page_bottom=24` 三个语义都是 24dp——「模块间距」与「欢迎区内边距」「页面底距」同值。缺少 32–40 的区块级（section）间距，无法表达「这是两个大区块之间的呼吸」。

**【为什么伤一致/美】** Geist 间距三段节奏：组内 8 / 组间 16 / 区块 32–40，4px 基。当前组间（`card_gap=12`）与区块间（`block=24`）只差一档，且 `block` 又和 `hero_inner` 等内边距撞值，导致页面从局部到全局的节奏是平的，大区块之间不够松，信息分组感弱。

**【建议】** 在 `dimens.xml` 补 `captain_space_section=32dp`（大区块之间，如「首页氛围区 ↔ 功能区」），把 `captain_space_block` 的语义明确为「模块内子块间距=24」，与 `section=32` 分层；`card_gap` 由 12 提到 16 对齐 4px 基与 Geist 组间档。三段节奏落地为组内 `space_inline=8` / 组间 `space_card_gap=16` / 区块 `space_section=32`。

**【验收】**
- [ ] `dimens.xml` 存在 `captain_space_section`（32–40dp）
- [ ] 大区块用 section、卡片之间用 card_gap、内边距用 card_inner/hero_inner，三者不再同值
- [ ] 首页从上到下间距呈现 8/16/32 的可辨节奏

---

### P2-12 交互态统一：press 三套并存，focus/disabled 缺失

**【现象】** 当前「按下态」有三套互不相干的实现：主壳走系统 `ripple`（`AppTheme`）、XHS 走 `selector` drawable、Timer 走自绘 `day?A:B`+alpha（P0-4）。`styles.xml` 的 `CaptainButton.Primary/Secondary` 只定义了 normal 背景（`bg_button_primary`/`bg_button_secondary`），**没有 pressed/focused/disabled** 状态。无任何可访问 focus 高亮。

**【为什么伤一致/美】** 同一个「按下」在三个模块深浅、形态各异，用户感知到的「这个 App 的点击反馈」是分裂的。缺 disabled 态导致不可用按钮与可用按钮看起来一样，缺 focus 态对键盘/无障碍用户不可用——这是可访问性硬伤。

**【建议】** 用 P1-5 状态色阶统一三套：
1. 主按钮 `bg_button_primary` 改为 `selector`：normal=`brand_700`、pressed=`brand_800`、disabled=`gray_300`+文字 `gray_500`、focused=描 `brand_500` 2dp 焦点环；次按钮同理走浅档。
2. XHS/Timer 的按下统一改取 `brand_800`/对应深档，Timer 不再手写 alpha。
3. 全 App 可点击控件补 `android:state_focused` 焦点态（2dp `brand_500` 描边），满足键盘/无障碍可见焦点。

**【验收】**
- [ ] 主壳/XHS/Timer 的 pressed 取自同一状态色阶档（brand_800）
- [ ] `bg_button_primary` 为 selector，含 normal/pressed/disabled/focused 四态
- [ ] disabled 按钮视觉明确区别于可用按钮
- [ ] 键盘遍历时每个可交互控件有可见焦点环

# 设计逻辑方法论(基于 Geist 抽象)

一份好的 `design.md` 不止是色号与字号的清单,它的真正价值在于把「设计思维」编码成机器可执行的约束:每一个 token 都是一条规则,而不是一次审美选择。其中最颠覆直觉的一条是——**颜色不是装饰,而是状态的表现形式**。当我们把这套思想抽象出来,它就不再绑定于某个具体产品,而成为一种任何团队(尤其是 AI 辅助编码场景)都能据此稳定产出一致界面的方法论。下面十条,各以「是什么 / 为什么 / 怎么落地」三段展开。

---

## 1. 核心命题:token 编码的是「意图/状态」,不是「色值」

**是什么。** 一个设计 token 的名字应该回答「这是什么角色」,而不是「这是什么颜色」。`button-background-hover` 是意图,`pink-400` 是色值。前者描述了系统中的一个语义位置,后者只是一个十六进制数。颜色被绑定到角色之后,它就成了角色当前状态的一种「表现」,而非可有可无的点缀。

**为什么。** 当 token 编码色值时,「改主题」意味着全局查找替换、人肉判断每一处该不该改;当 token 编码意图时,换肤只是替换一张映射表,结构纹丝不动。更关键的是对 AI 编码的意义:模型看到 `text-error` 能推断出「这里要表达一个错误文字」,从而在新页面里复用同一意图;但看到 `#E45B5B` 它只能复制粘贴,无法泛化。意图是可推理的,色值不是。

**怎么落地。** 命名一律采用「语义 + 角色 + 状态」三段式,禁止在组件层直接写裸色值。任何一处颜色出现前,先问一句:它在表达什么状态?如果答不上来,说明这个颜色不该存在,或者缺了一个 token。

---

## 2. 状态色阶:每色 100→1000 十档,四段意图

**是什么。** 同一语义色不是一个值,而是一条从 100 到 1000 的十档色阶。这十档不是均匀渐变的装饰梯度,而是被切成四个意图段:**100–300 背景态**(默认 / 悬停 / 按下三级)、**400–600 边框态**、**700–800 实心填充态**、**900–1000 文字与图标层级**。每一档都有钦定的用途。

**为什么。** 设计中最大的隐性成本是「猜」:悬停时背景该深多少?按下时再深多少?边框比背景深几度?没有色阶时,这些全靠每个人现场拍脑袋,于是同一个交互在十个页面有十种深浅。把色阶按意图分段后,「默认 100、悬停 200、按下 300」成为一条确定的规则,猜测被消灭,一致性由结构保证而非由 reviewer 的眼力保证。

**怎么落地。** 为每个语义色生成完整十档,并在文档里把每一档标注用途(如 `brand-200 = 悬停背景`)。组件状态机直接引用档位:`:hover` 取 +100、`:active` 取 +200,边框固定取 400–600 段,实心按钮取 700–800,其上文字取 1000。一旦定档,交互状态就不再是设计问题而是查表问题。

---

## 3. 两个正交维度:语义 × 状态 = token

**是什么。** 整个颜色系统由两个互相独立的维度张成:**语义维度**(brand / gray / red / green / blue……回答「这是什么含义」)与**状态维度**(100–1000 十档,回答「它现在处于什么状态」)。任意一个具体 token,都是这两维的一个交点:`red-700` = 语义 red × 状态 700。

**为什么。** 正交意味着两维可以各自独立演化:新增一种语义(比如加个 `purple`),只需补一列,十档状态规则自动套用;调整状态分段策略,所有语义同步受益。这是一种乘法式的可扩展性——`N 个语义 × 10 档` 覆盖 `N×10` 种场景,却只需维护 `N + 10` 份规则。对 AI 而言,这种结构化网格极易学习与填充。

**怎么落地。** 用一张二维表来组织 token:行是语义,列是状态。新建颜色时先确认它落在哪个语义行,再按状态列取档,绝不允许凭空造一个游离于网格之外的颜色。任何「特例色」都应被追问:它到底属于哪个语义?是不是某个状态档?

---

## 4. 排版四件套:heading / label / copy / button 各自成阶

**是什么。** 文字不是一个 `font-size` 的连续滑杆,而是四类各自独立的阶梯:**heading**(标题)、**label**(标签 / 表单标识)、**copy**(正文)、**button**(按钮文字)。每一类都有自己的若干档,每一档是字号、字重、行高、字距四个属性协同调好的一个「组合包」,而非单一维度。

**为什么。** 把所有层级压在一个字号轴上、靠「加粗」区分主次,是排版失控的根源:标题和正文用同一字重只是大小不同,层级感薄弱;不同语境(密集表单 vs 舒展正文)需要不同的行高,单轴无法表达。四件套各自成阶,让「这是一个标题」与「这是一段正文」从结构上就不同,而不只是大了 2px。

**怎么落地。** 为四类各定义一组命名档(如 `heading-1…4`、`copy-default / copy-small`),每档同时锁定四个属性,组件只能整包引用、不许单独覆盖某一项。需要强调时,改用更高一档或换 label 类型,而不是手动 `bold` 一下。

---

## 5. 间距三段节奏:组内 8 / 组间 16 / 区块 32–40,4px 基

**是什么。** 间距遵循一套有节奏的三段制,全部建立在 4px 基准网格上:**组内元素 8**(关系紧密)、**相邻组之间 16**(关系并列)、**大区块之间 32–40**(关系分隔)。间距大小本身就在传达「这些东西有多亲近」。

**为什么。** 间距是无形的信息架构。当所有空隙都是随手填的 10、14、18,界面会显得「松散但说不清哪里不对」——因为亲疏关系被噪声淹没了。三段节奏让留白承担分组职责:用户(和 AI)不需要看边框,光凭间距就能读出层级。4px 基准则保证所有间距互相成倍数,天然对齐。

**怎么落地。** 只暴露少量间距 token(对应 8 / 16 / 32–40 三段及其 4px 倍数衍生值),禁用任意数值。布局时先判断元素间的关系强度,再据此选段,而不是先看着顺眼再调数。

---

## 6. 圆角克制:日常 6 / 菜单 12 / 全屏 16 / pill 9999,不混用

**是什么。** 圆角是一套有限且按场景钦定的离散值:**日常控件 6**(按钮 / 输入框 / 卡片)、**菜单与浮层 12**、**全屏容器 / 大面板 16**、**胶囊形 pill 9999**。每种容器类型对应一个固定半径。

**为什么。** 圆角混用是廉价感的主要来源之一:同一屏里按钮 8、卡片 11、弹窗 14,差异小到不构成风格、大到破坏统一,只剩杂乱。把半径离散化并与容器层级绑定后,圆角变成一种可读的语言——大容器更圆、小控件更利落、pill 表示「这是个标签/开关」。

**怎么落地。** 定义这四个半径 token 即封顶,不再新增中间值。组件按其「容器类型」取对应档,同一类型在全产品共用同一半径。出现第五个圆角值时,应先质疑它是不是某个已有类型的误用。

---

## 7. elevation 三档:卡片 / 弹层 / 模态,深浅主题各一套

**是什么。** 阴影(elevation)不是任意的视觉糖,而是三个表达「层级高度」的离散档:**卡片**(轻微抬起,贴着页面)、**弹层 / 下拉**(浮在内容之上)、**模态 / 对话框**(凌驾全局)。并且深色与浅色主题各配一套——同样的「高度」在两种背景下需要不同的阴影参数才能读出来。

**为什么。** elevation 编码的是 z 轴上的层级关系:越高表示越「临时、越需要被关注、越优先接收交互」。只有一个阴影值时,卡片和模态视觉上一样高,层级语义丢失。深浅各一套则是因为暗色背景下纯黑阴影几乎不可见,常需改用「更亮的边缘高光」来表达抬升——这是结构相同、映射不同的典型例子(呼应第 10 条)。

**怎么落地。** 定义三档 elevation token,每档在浅色与深色主题下分别给定参数。组件按其层级角色取档:静态内容用卡片档,临时浮层用弹层档,阻断式交互用模态档。不允许为「看起来更立体」而手调阴影。

---

## 8. 动效只服务于「说明变化」:默认 0ms,状态 150 / 弹层 200 / 遮罩 300

**是什么。** 动效的唯一职责是解释「发生了什么变化」,不是炫技。默认时长为 **0ms**(即:大多数变化不该有动画),仅在需要交代变化的场景按类型给固定时长——**状态切换 150ms、弹层进出 200ms、遮罩 / 大面积过渡 300ms**——并配标准缓动曲线,同时尊重系统的 `prefers-reduced-motion`。

**为什么。** 动效本质是在「占用用户的时间」换取「让变化可被理解」。如果一个变化本身一目了然(如纯文字替换),动画就是纯损耗——所以默认 0。需要动画时,时长应与位移幅度匹配:微小状态变化要快(150),大面积遮挡需要稍慢以建立空间感(300)。把这些定成 token,既防止「随手 300ms 全场飘」,也保证节奏统一。无障碍诉求则要求所有动效可被一键降级。

**怎么落地。** 定义 `motion-fast/medium/slow`(150/200/300)与标准缓动 token,默认不加动画,加时必须从这三档里选并说明它在解释哪个变化。统一在一处实现 reduced-motion 降级:命中时将所有时长归零或大幅缩短。

---

## 9. 文案规则:动词 + 名词;错误说清「发生了什么 + 怎么办」

**是什么。** 文案也是设计的一部分,同样受 token 化的规则约束。操作文案用「**动词 + 名词**」(如「保存草稿」而非「确定」);错误文案必须同时交代**发生了什么**和**下一步怎么办**;并主动**去掉「成功」「请」**这类空词。

**为什么。** 「确定 / 取消」这类泛词把判断成本转嫁给用户;「动词 + 名词」让按钮自带后果说明,降低误操作。错误信息若只说「操作失败」,用户被困在原地——必须给出可执行的出路。而「保存成功」的「成功」是冗余的(界面状态已经证明了),「请稍候」的「请」是客套噪声——删掉它们,信息密度更高、语气更平等。

**怎么落地。** 在文档里给出可照抄的句式模板与正反例对照表(✅ 保存草稿 / ❌ 确定;✅ 网络超时,请检查连接后重试 / ❌ 操作失败)。评审与 AI 生成文案时直接对照模板检查,把语言风格变成可校验的规则而非语感。

---

## 10. 双主题对称:同一套语义 + 状态,深浅只换映射不换结构

**是什么。** 深色与浅色主题不是两份独立设计,而是同一套「语义 × 状态」网格的两种映射。结构(有哪些语义、哪些状态档、组件引用哪个 token)完全一致,**深浅之间只替换 token 到具体值的对照表**,不改任何引用关系。

**为什么。** 这是前九条的逻辑终点,也是「token 编码意图而非色值」最有力的回报:正因为组件引用的是 `surface-default` 而非 `#FFFFFF`,切换主题才只需换映射、无需碰组件。若两套主题各自硬编码,它们会随时间各自漂移、永久双倍维护成本,且新功能必然漏配其中一套。对称性把主题从「两份设计」降维成「一份设计 + 两张映射表」。

**怎么落地。** 维持单一 token 结构,深浅各提供一份「语义 → 值」映射文件;组件层永远引用语义 token,从不出现 `if dark then A else B` 的条件分支。出现这种条件硬编码,即是结构泄漏的信号——应把分叉收回到映射表里。

## 落到船长 App

把上面的方法论对照船长 App 的现状(已读 `colors.xml`、`dimens.xml`、`styles.xml`),可以清楚地看到:**船长已经走完了「语义层」,但还没进入「状态层」**。

**已经具备的(语义维度 + 部分一维阶梯):**

- **语义颜色层**完整。`colors.xml` 里已有成体系的 `captain_brand_*`(primary/accent/support_success)、`captain_surface_*`(page/hero/card/card_soft/icon_tile/toolbar)、`captain_text_*`(primary/secondary/tertiary/on_brand/on_soft)、`captain_feedback_*`(error/warning/success/info)。这正是第 1、3 条所说的「语义维度」,命名也确实编码了意图而非色值。
- **间距与圆角阶**已存在雏形。`dimens.xml` 有 `captain_space_*`(inline 8 / card_inner 16 / block 24……)对应第 5 条的节奏感,`captain_radius_*`(button 14 / card 16 / card_large 20 / badge 12)对应第 6 条的离散圆角。
- **排版**通过 `styles.xml` 的 `CaptainText.*`(Hero/PageTitle/CardTitle/Body/Caption/Overline)做了分层,接近第 4 条的「各自成阶」。

**结构性缺口(尚未进入的维度):**

1. **缺状态层——这是最核心的缺口。** 整个 `colors.xml` 里,每个语义色都**只有一个值**:`captain_brand_primary` 就一个 `#F56B7D`,没有 hover、没有 pressed、没有配套的边框档。边框只有 `captain_border_soft / strong` 两个孤立值,不成色阶。对照第 2、3 条,船长缺的正是**状态这一整个正交维度**——目前是「语义 × 1」,而方法论要求「语义 × 10」。后果就是第 2 条点名的病:每个按钮的按下态深多少,只能在各个 `bg_button_*` drawable 里各自硬编码、各自猜。

2. **缺 elevation 阶。** `dimens.xml` 里与高度相关的只有 `captain_elevation_tab_shell`(10dp)**孤零零一个值**,且是为 tab 外壳特配的,并非通用层级体系。对照第 7 条的「卡片 / 弹层 / 模态」三档,船长既没有分档,也谈不上深浅两套,卡片与未来的弹窗在 z 轴上无法被区分。

3. **完全没有 motion token。** 三份资源文件里**找不到任何动效时长或缓动定义**。对照第 8 条,船长目前的动画(若有)只能散落在各处 Java 代码里手写时长,既无 150/200/300 的统一节奏,也没有集中的 reduced-motion 降级开关。

4. **没有双主题对称,且已出现「结构泄漏」的征兆。** 当前只有一套浅色 token,无暗色映射。更值得警惕的是 Timer 频道里 `day ? A : B` 式的硬编码配色——这本质上**就是第 10 条所禁止的「条件分支硬编码」**:它其实是一个「被困在自定义 Canvas 绘制里、没有被抽出来的暗色状态层」。换句话说,船长并非不需要状态层和暗色映射,而是已经在用最坏的方式(散落的三元表达式)临时实现它们。把这些分叉收回成 token 映射表,正是第 2、10 条要解决的问题。

**结论与下一步。** 船长走完了语义层,接下来的关键一步是**给每个语义色补齐 100→1000 的状态色阶**(尤其是 brand、gray/surface、feedback 三组的 hover / pressed / border 档),让交互状态从「各 drawable 里猜」变成「查档」;同步补 elevation 三档与 motion 三档 token;最后把 Timer 的 `day?A:B` 从 Java 里抽出来,统一成「同结构、双映射」的浅/深两套,完成第 10 条的对称收口。

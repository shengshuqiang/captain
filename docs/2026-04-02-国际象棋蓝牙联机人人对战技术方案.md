# 2026-04-02 国际象棋蓝牙联机人人对战技术方案

## 1. 文档目标

本文档用于指导船长 App 新增“国际象棋”功能模块的设计与开发，目标是在当前 Android 原生工程内落地一个：

- 与“资源嗅探”平级的首页功能入口
- 支持两台设备蓝牙直连的人人对战
- 支持选择执棋方、设置用户名与头像
- 支持保存用户资料、历史对战记录
- 支持完整复盘回放
- 支持完整国际象棋规则校验
- UI 风格符合当前工程主壳层设计规范
- 整体观感简洁、美观、儿童友好，适合 `9+` 用户

本文档不涉及代码实现，只输出可直接进入开发阶段的技术方案。

## 2. 需求边界

### 2.1 本期必须支持

1. 首页新增“国际象棋”入口，层级与“资源嗅探”一致。
2. 两台 Android 设备通过局域网蓝牙直连对战。
3. 用户可以设置用户名。
4. 用户可以设置头像。
5. 用户可以选择执白、执黑或随机。
6. 对局过程具备完整规则校验。
7. 历史对局可持久化保存。
8. 历史对局可逐步回放复盘。
9. UI 风格符合现有 `captain_*` 视觉 token。

### 2.2 本期明确不做

1. 不做 AI 对战。
2. 不做联网账号体系。
3. 不做多人观战。
4. 不做语音、自由聊天、表情包聊天。
5. 不做残局续局和断线自动重连。
6. 不做棋力分析、胜率曲线、AI 点评。
7. 不做 iOS 或跨端互通。

### 2.3 关键产品取舍

1. 平台范围锁定为当前 Android 原生工程。
2. 复盘能力锁定为“交互式棋盘回放”，不做 AI 复盘分析。
3. 头像方案采用“原创赛车感卡通预设头像 + 本地相册自选”，不直接使用第三方 IP 角色素材。

## 4. 功能结构设计

### 4.1 新模块包结构

建议新增独立子域：

```text
com.shuqiang.captain.chess
├── ui
├── bt
├── domain
├── data
└── model
```

职责划分如下：

- `ui`：页面、适配器、自定义棋盘 View、对局交互
- `bt`：蓝牙发现、配对、连接、消息收发、会话状态
- `domain`：规则引擎封装、对局状态机、结果判定
- `data`：本地资料、历史对局、头像文件、棋谱存储
- `model`：协议消息、用户信息、对局快照、历史实体

### 4.2 页面流设计

本期固定为 5 个页面：

1. `ChessOnboardingActivity`
   - 首次进入时设置用户名和头像
2. `ChessLobbyActivity`
   - 创建对局、加入对局、选边、搜设备、连接设备
3. `ChessGameActivity`
   - 棋盘对局页
4. `ChessHistoryActivity`
   - 历史对局列表
5. `ChessReplayActivity`
   - 复盘回放页

页面关系如下：

```text
首页卡片 -> ChessOnboardingActivity(首次)
         -> ChessLobbyActivity(已初始化)

ChessLobbyActivity -> ChessGameActivity
ChessLobbyActivity -> ChessHistoryActivity
ChessHistoryActivity -> ChessReplayActivity
ChessGameActivity -> ChessReplayActivity(终局后可直达)
```

## 5. 蓝牙联机方案

### 5.1 方案选型

本期采用 `Bluetooth Classic RFCOMM`，不采用 BLE。

原因：

1. 本场景属于双端持续连接、低频但持续交换状态数据，更适合 Classic Socket 模型。
2. 双端人人对战需要稳定会话、房主与客户端的明确连接关系，RFCOMM 更贴近传统 client/server。
3. BLE 更适合低功耗、小数据广播式场景，本需求不需要 BLE 的功耗优势。

### 5.2 联机角色模型

固定采用“单房主权威模型”：

- 创建房间的一方为 `Host`
- 加入房间的一方为 `Peer`
- 只有 `Host` 负责最终规则校验和结果裁定
- `Peer` 发送操作请求，不做最终裁定

这样做的目的：

1. 避免双端同时判定导致状态漂移。
2. 断连、非法走子、终局判断都能以一个权威源为准。
3. 历史棋谱生成逻辑只有一套，简单且稳定。

### 5.3 配对与发现流程

建议采用两层策略：

1. API 26+ 优先使用 `Companion Device Manager` 做配对发现。
2. 若 CDM 不可用或失败，则回退经典 `BluetoothAdapter.startDiscovery()`。

联机流程：

1. Host 进入建房态，开启 RFCOMM `BluetoothServerSocket`
2. Peer 搜索设备并选择 Host
3. 完成蓝牙配对
4. Peer 发起 `BluetoothSocket.connect()`
5. Host `accept()` 成功后建立会话
6. 双方交换用户资料、选边意图、协议版本
7. Host 下发开局状态

### 5.4 执棋方选择

联机大厅固定支持 3 种选项：

- 执白
- 执黑
- 随机

规则如下：

1. Host 创建时先声明自己的选边意图。
2. Peer 加入后只能选择兼容的剩余选项。
3. 若任一方选择随机，则由 Host 负责最终分配。
4. 开局结果以 Host 下发的 `START_GAME` 为准。

### 5.5 消息协议

传输层采用：

- RFCOMM 长连接
- 长度前缀 + JSON 文本消息
- `Gson` 序列化/反序列化

消息类型固定为：

1. `HELLO`
2. `READY`
3. `START_GAME`
4. `MOVE_REQUEST`
5. `MOVE_COMMIT`
6. `DRAW_OFFER`
7. `DRAW_RESPONSE`
8. `RESIGN`
9. `SYNC_STATE`
10. `HEARTBEAT`
11. `END_GAME`

#### 5.5.1 关键消息字段

`HELLO`

- `protocolVersion`
- `username`
- `avatar`
- `seatPreference`
- `deviceName`

`MOVE_REQUEST`

- `gameId`
- `from`
- `to`
- `promotion`
- `clientMoveIndex`

`MOVE_COMMIT`

- `gameId`
- `approved`
- `uci`
- `san`
- `fen`
- `result`
- `terminationReason`
- `moveIndex`

`SYNC_STATE`

- `gameId`
- `fen`
- `pgn`
- `moveIndex`
- `activeColor`

### 5.6 断连策略

本期固定策略：

1. 一旦蓝牙链路断开，当前联机会话立即结束。
2. 双方均标记本局为 `ABORTED`，并保存当时最后同步状态。
3. 不做自动重连。
4. 不做残局续局。
5. 用户可在历史中查看并复盘已保存走子。

## 6. 国际象棋规则引擎方案

### 6.1 规则目标

必须满足“完整国际象棋规则校验”。

本期至少覆盖：

1. 普通合法走子
2. 吃子
3. 将军
4. 将死
5. 逼和
6. 王车易位
7. 吃过路兵
8. 兵升变
9. 子力不足和棋
10. 三次重复申请和棋
11. 五次重复自动和棋
12. 50 步申请和棋
13. 75 步自动和棋
14. 认输
15. 求和

### 6.2 引擎选型

规则层建议引入成熟 Java 棋类库 `chesslib`：

- 用于合法走子校验
- 用于 FEN 读写
- 用于 PGN 生成基础
- 用于棋盘状态重放

业务层再补一层 `ChessRuleEngine` 与 `TerminationEvaluator`，原因如下：

1. 对局 UI、联机协议和业务文案不能直接依赖三方库对象。
2. 终局分类需要和产品展示字段对齐。
3. 三次重复、50 步这类申请型和棋，需要显式业务层处理。

### 6.3 规则判定模型

#### 6.3.1 走子输入格式

联机与内部状态统一使用：

- 传输格式：`UCI`
- 展示格式：`SAN`
- 存档格式：`PGN + finalFEN`

#### 6.3.2 兵升变

兵到达底线后必须弹出升变选择弹层，仅提供：

- 后
- 车
- 象
- 马

禁止默认静默升后。

#### 6.3.3 终局原因枚举

建议统一终局原因：

- `CHECKMATE`
- `STALEMATE`
- `DRAW_AGREEMENT`
- `THREEFOLD_REPETITION_CLAIM`
- `FIVEFOLD_REPETITION_AUTO`
- `FIFTY_MOVE_CLAIM`
- `SEVENTY_FIVE_MOVE_AUTO`
- `INSUFFICIENT_MATERIAL`
- `RESIGNATION`
- `ABORTED`

### 6.4 对局状态机

建议状态机如下：

```text
IDLE
-> MATCHING
-> CONNECTED
-> READY
-> PLAYING
-> FINISHED
-> REPLAY
```

`PLAYING` 内部子状态：

- `MY_TURN`
- `OPPONENT_TURN`
- `PROMOTION_PENDING`
- `DRAW_OFFER_PENDING`
- `SYNCING`

## 7. 数据持久化方案

### 7.1 用户资料存储

用户资料是轻量配置，适合单独存入 `SharedPreferences`。

建议新建：

- `captain_chess_prefs`

字段：

- `username`
- `avatar_type`
- `avatar_value`
- `last_seat_preference`
- `last_device_mac`
- `has_completed_onboarding`

其中：

- `avatar_type`：`PRESET` 或 `LOCAL`
- `avatar_value`：预设头像资源名或本地头像相对路径

### 7.2 历史对局存储

历史对局不适合继续塞进 `SharedPreferences`，建议独立使用 `SQLiteOpenHelper`。

原因：

1. 对局历史是列表型、可增长数据。
2. 需要按时间倒序查询。
3. 需要保存较长文本，如 PGN。
4. 后续可能增加筛选或统计字段。

建议数据库：

- `captain_chess.db`

建议表：

#### 7.2.1 `games`

- `game_id`
- `started_at`
- `ended_at`
- `my_username`
- `my_avatar_snapshot`
- `opponent_username`
- `opponent_avatar_snapshot`
- `my_color`
- `result`
- `termination_reason`
- `move_count`
- `final_fen`
- `pgn_text`
- `aborted_flag`

#### 7.2.2 `moves`（可选）

若后续需要更细颗粒检索，可拆子表：

- `id`
- `game_id`
- `move_index`
- `uci`
- `san`
- `fen_after_move`
- `clock_ms`（本期可先不启用）

本期为了简化实现，可以先只存 `games` 表，走子明细由 `PGN` 回放生成。

### 7.3 头像文件存储

本地相册头像处理流程：

1. 调起 `pictureselector` 单图选择
2. 裁成 `1:1`
3. 压缩为统一小尺寸，如 `256 x 256`
4. 保存到 app-private 目录
5. 仅记录相对路径

这样可以避免：

1. 原图过大占空间
2. 媒体库删除后路径失效
3. 外部 Uri 长期不可读

## 8. 复盘方案

### 8.1 复盘能力边界

本期复盘提供：

1. 棋盘状态回看
2. 上一步 / 下一步
3. 跳到开局 / 跳到终局
4. 展示当前回合走子 SAN 文本
5. 展示终局结果与原因
6. 支持翻转棋盘

本期不提供：

1. AI 最佳着推荐
2. 胜率图
3. 错误着法分析
4. PGN 导出按钮

### 8.2 复盘实现方式

复盘页加载历史记录中的：

- `pgn_text`
- `final_fen`
- 双方资料快照

再通过 `ChessRuleEngine` 按顺序重建每一步棋盘状态，形成：

- `List<ReplayFrame>`

每个 `ReplayFrame` 包含：

- `moveIndex`
- `san`
- `fen`
- `activeColor`
- `isCheck`
- `capturedPiece`
- `promotion`

UI 只负责按索引切换 `ReplayFrame`。

## 9. UI/UX 方案

### 9.1 总体原则

本功能的 UI 风格目标是：

- 简洁
- 干净
- 轻松
- 明快
- 儿童友好
- 适合 9+ 用户

但必须避免：

- 过幼态
- 过度花哨
- 过度糖果色
- 过多动画干扰
- 牺牲棋盘识别度

### 9.2 与当前壳层规范的关系

本功能属于主壳层新增模块，必须服从现有设计规范，而不是“游戏子系统另起一套视觉语言”。

因此：

1. 页面背景继续使用 `captain_surface_page`
2. 卡片和容器继续使用 `captain_surface_card`
3. 主强调色继续使用 `captain_brand_primary`
4. 辅助强调可用 `captain_brand_accent`
5. 文字层级继续复用 `CaptainText.*`
6. 按钮继续复用 `CaptainButton.Primary/Secondary`

### 9.3 儿童棋类 UI 最佳实践落地方向

业界儿童棋类产品在 UI 上有几个共同原则，本方案按工程可执行方式落地：

1. 首任务清晰  
   首屏只放“创建对局”“加入对局”“历史复盘”三类任务，不堆功能墙。

2. 大交互目标  
   关键按钮、棋盘格、弹窗主操作都保证足够点击面积。

3. 状态反馈直白  
   当前轮到谁、是否将军、是否非法、是否断开，不靠用户猜。

4. 装饰轻量  
   儿童友好主要靠头像、轻插画、轻标签点缀，而不是让棋盘本身花哨。

5. 识别优先  
   棋子和棋盘必须比头像和装饰更重要，避免儿童误读局面。

### 9.4 棋盘视觉方案

#### 9.4.1 棋盘

棋盘建议：

1. 浅暖色与中性深色两类格子形成明确对比。
2. 当前选中格、合法落点格、上一步来源/目标格使用清晰高亮。
3. 行列坐标可选显示，默认开启。
4. 棋盘边框采用轻圆角容器，不直接把格子做成过软圆角。

#### 9.4.2 棋子

棋子建议：

1. 轮廓接近标准 Staunton 识别体系。
2. 适度圆角与轻阴影，提高亲和力。
3. 白棋与黑棋对比清楚。
4. 禁止使用过于卡通的拟人化表情棋子。

### 9.5 大厅页设计

大厅页建议结构：

1. 顶部轻 Hero 区
   - 标题：国际象棋
   - 副标题：蓝牙直连，和身边的人来一局

2. 用户资料卡
   - 头像
   - 用户名
   - 编辑入口

3. 对战卡片区
   - 创建对局
   - 加入对局
   - 历史对局

4. 设备连接状态区
   - 蓝牙是否开启
   - 当前搜索状态
   - 已选设备

### 9.6 对局页设计

对局页结构固定为：

1. 顶部玩家信息条
   - 对手头像、名字、执棋方
   - 当前状态标签

2. 中部棋盘区
   - 棋盘优先，占最大空间

3. 底部操作区
   - 求和
   - 认输
   - 返回历史（仅终局后）

4. 底部状态文案
   - 轮到谁
   - 将军提示
   - 非法走子提示

### 9.7 历史页与复盘页设计

历史页建议采用卡片列表：

- 对手头像
- 对手用户名
- 我方执棋颜色
- 对局结果
- 结束原因
- 对局时间
- “复盘本局”按钮

复盘页保持极简：

- 顶部结果摘要
- 中部棋盘
- 底部步进控制
- 当前步数与 SAN 文本

### 9.8 头像风格方案

预设头像固定采用“原创赛车感卡通头像组”。

方向要求：

1. 圆润、明亮、识别度高
2. 不直接复用外部版权角色
3. 男女都可接受
4. 适合儿童但不幼稚
5. 统一描边、统一色温、统一背景形状

建议预设 8 到 12 个头像：

- 头盔小车手
- 红色赛车帽
- 蓝色闪电护目镜
- 绿色冲刺头盔
- 黄色星星头盔
- 紫色机械护目镜
- 橙色冲线旗手
- 薄荷色维修小能手

### 10.1 当前版本线

当前工程 `targetSdkVersion=29`，本期落地需兼容：

- 后续升级到 Android 12+ 时的 Nearby Devices 权限模型

### 10.2 权限策略

1. `BLUETOOTH`
2. `BLUETOOTH_ADMIN`
3. `BLUETOOTH_SCAN`
4. `BLUETOOTH_CONNECT`
5. `BLUETOOTH_ADVERTISE`

运行时逻辑按系统版本分支：

1. Android 11 及以下
   - 蓝牙扫描相关权限按旧模型处理
2. Android 12 及以上
   - 走 Nearby Devices 权限申请

### 10.3 权限封装建议

当前工程只有相机/存储权限封装，没有蓝牙权限封装。

因此建议新增独立蓝牙权限管理器：

- `ChessBluetoothPermissionManager`

负责：

1. 蓝牙开关检测
2. 运行时权限检查
3. 权限说明弹窗文案
4. 页面内回调状态分发

## 14. 风险与待确认

### 14.1 主要风险

1. 当前工程蓝牙权限封装为空白，Android 12+ 兼容细节需要单独处理。
2. 规则“完整支持”如果完全手写，风险高，因此必须基于成熟棋类库实现。
3. 棋盘与联机状态同步如果做成双端都可裁定，容易漂移，因此必须坚持 Host 权威模型。
4. 儿童友好风格若执行过度，容易破坏棋类识别度，必须坚持“棋盘优先、装饰后置”。

### 14.2 当前默认结论

1. 技术架构采用“独立 chess 子域 + 轻接入主壳层”。
2. 联机协议采用 Bluetooth Classic RFCOMM。
3. 规则层采用 `chesslib + 业务封装`。
4. 用户资料使用 `SharedPreferences`，历史记录使用 `SQLiteOpenHelper`。
5. 头像使用“原创赛车感卡通预设头像 + 本地相册自选”。
6. 复盘范围锁定为交互式棋盘回放。
